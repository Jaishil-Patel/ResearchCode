Can a photogrammetry-reconstructed digital twin of the deployment environment measurably narrow the sim-to-real gap for Pepper's navigation policy?

The bet: policies trained in a world reconstructed from the actual room transfer better than policies trained in a generic one. Everything in this talk exists to make that comparison possible.

Phase 1 · complete

A reproducible research environment

Host

Ubuntu 22.04 on WSL2

Linux-native ROS tooling on Windows hardware, with WSLg for GPU-accelerated Gazebo rendering — no dual boot, no VM overhead.

Middleware

ROS 2 Humble

The current LTS. Chosen over Galactic (EOL) despite most Pepper packages targeting Galactic — that mismatch is the work on slide 8.

Simulator

Ignition Gazebo Fortress

Pairs with Humble, and is what the Pepper digital-twin stack was authored against. Successor to Gazebo Classic.

Build

colcon workspace

ros2_ws/ with --merge-install --symlink-install, Release build type. Dependencies pulled by vcstool and rosdep.

Tooling

VS Code Remote + git

Editing on Windows, executing in Linux, one filesystem. Version control on the workspace, not on generated artefacts.

Why it matters

Portability of results

A sim2real claim is only meaningful if the simulation is reproducible. Pinning the stack now is what makes the Phase 9 comparison defensible.

Phase 2 · complete

Learning the graph on a toy, to debug it on the robot

hello_ros is a minimal package — a publisher pushing std_msgs/String onto /greetings at 1 Hz, and a matching subscriber. The package is not the point. The introspection vocabulary is.

  • ros2 node info — what a node publishes, subscribes, and serves
  • ros2 topic hz — is the sensor actually running at rate?
  • ros2 topic echo — is the message content sane?
  • ros2 topic type — do the two ends agree on the interface?

These are the same four commands I use on the next slides to answer "is Pepper publishing odometry", "is the bridge alive", "is my RL node actually reaching Gazebo".

$ ros2 node list
/greeting_publisher
/greeting_subscriber
$ ros2 topic hz /greetings
average rate: 1.000
$ ros2 topic type /greetings
std_msgs/msg/String
# later, the same commands on:
# /scan /odom /cmd_vel /joint_states
Phase 3 · decision

Choosing a Pepper stack was a research decision, not a download

Pepper's open-source ecosystem is fragmented: most packages are ROS 1 only, several target Gazebo Classic, and many are unmaintained. Committing to the wrong one costs a mid-project migration. I evaluated against four criteria before writing any code on top.

Criterion 01

ROS 2 native

No ROS 1 bridge in the loop — it would sit between the policy and the robot in exactly the place latency matters.

Criterion 02

Simulation-first

A full physics-capable model with collision geometry and controllers, not just a visual URDF.

Criterion 03

Path to hardware

A credible route to the physical Pepper, so Phase 9 is not a rewrite.

Criterion 04

Provenance

Maintained, and ideally validated in the literature rather than an unreviewed hobby port.

Selected: pepper_ign_moveit2 — the Pepper open-source digital twin

Sekkat, Moutik, El Kari, Chaibi, Tchakoucht & El Hilali (2024). Beyond simulation: unlocking the frontiers of humanoid robot capability and intelligence with Pepper's open-source digital twin. Heliyon 10(14). Ignition Gazebo + MoveIt 2 + ros2_control, peer-reviewed — with one catch, next slide.

Phase 3 · the actual engineering

Porting the stack: Galactic + Docker → Humble + WSL2

The upstream repository targets ROS 2 Galactic inside a Docker container with an NVIDIA GPU. I run Humble on WSL2. It did not build, and when it did, the model was wrong. Five distinct classes of defect:

Missing inertia l_gripper and r_gripper links carried no <inertial> block — physics rejects massless dynamic links. Added mass 1e-5, inertia 1e-35.
Mirrored joints Sign errors on the right arm: RShoulderRoll 0.17 → −0.17 and RElbowRoll −0.17 → 0.17. The robot spawned in a physically impossible pose.
Xacro API drift load_yaml(...) → xacro.load_yaml(...) in the ros2_control macro — the function moved between Galactic and Humble.
Container paths The ign_ros2_control plugin hardcoded its <parameters> path to /root/ws/..., valid only inside the author's Docker image. Repointed to the local workspace.
WSL2 graphics Added /dev/dxg detection, /mnt/wslg mounts and WAYLAND_DISPLAY passthrough for GPU rendering; replaced a mesh symlink that Windows could not resolve.

Phase 3 · outcome

What I can now build on

Kinematics

Full xacro chain

Arms, head, legs, wheels, torso, fingers and sensor frames, generating both URDF and SDF at build time — plus ~50 STL collision and ~50 DAE visual meshes.

Control

6 trajectory controllers

Head, torso, left/right arm, left/right hand — with a joint state broadcaster at 250 Hz, over ign_ros2_control. DiffDrive and PosePublisher plugins on the base.

Planning

MoveIt 2, configured

OMPL planning pipeline, kinematics solver, joint limits and servo config already tuned for Pepper's arms — I did not have to author an SRDF.

Integration

Gazebo ↔ ROS bridge

A parameterised bridge covering clock, joint states, trajectories, odometry, TF and cmd_vel — the exact seam the RL node will plug into.

Entry points

Three launch modes

gz.launch.py for full simulation, fake.launch.py for mock hardware in RViz alone, view.launch.py to inspect the model.

Proof of life

A working demo

ex_follow_target.py — drag a target in Gazebo and the arm plans to it through MoveIt 2. An end-to-end path from GUI to controller.

Named before you ask

Four open technical risks

Blocking The robot has no simulated sensors. pepper_robot.gazebo declares laser, camera, sonar and IMU positions as TF frames, but contains no <sensor> elements — so nothing publishes. My observation space depends on /scan. Adding simulated sensors is a prerequisite for Phase 7, not a detail, and it is now the first item on the roadmap.
Active Dependencies pinned to Galactic branches. ros_ign, gz_ros2_control and ros2_controllers are all checked out on Galactic refs while the workspace runs Humble. It compiles; runtime behaviour is what I am validating this week.
Watch Pepper's base is omnidirectional; the plugin is DiffDrive. A differential-drive model cannot express lateral motion. If the action space is (vx, vy, ω), the base plugin has to change — which alters what transfers to hardware.
Watch One world file exists. Only follow_target.sdf, an arm-manipulation scene. Navigation worlds are Phase 5 and the photogrammetry world is Phase 6 — neither exists yet.

The scaffolding is deliberate — it mirrors Phases 6 through 8 — but it is empty, and I would rather say so than imply otherwise. Concretely, as of today there is:

  • no reinforcement learning code, no train.py, no SAC agent
  • no Gym environment, no defined observation, action or reward
  • no photogrammetry capture and no reconstructed mesh
  • no experiments run — no checkpoints, rosbags, logs or plots anywhere
  • no NAOqi interface to the physical robot

What exists is the platform those things need. The argument of this talk is that the platform was the expensive part to get right, not that the research is done.

What I need

Four things I need decided

Physical Pepper access

When can I book time with the robot, and for how long? Phase 9 needs repeated runs in the same room, not a single session. Knowing the constraint now shapes how I design the evaluation.

Photogrammetry capture

Which room are we committing to, can it be booked and kept static, and what capture equipment is available? The room is the independent variable of the whole study.

Compute for training

SAC over a physics simulator is expensive. Is there lab or cluster GPU time, or should I design the experiment around a single workstation?

The evaluation metric

I would like agreement now on what "closing the gap" means — success rate, path efficiency, collision count, or a composite. Fixing it before training avoids choosing the metric that flatters the result.
